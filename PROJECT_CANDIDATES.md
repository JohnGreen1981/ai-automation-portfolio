# Кандидаты для портфолио

Источник: проектные карточки в глобальной wiki, домен `projects/it`.

Цель файла — подготовить обсуждение, какие проекты показывать в GitHub-портфолио. Это не финальный выбор кейсов.

## Критерии отбора

- Проект должен показывать реальный workflow, а не только учебный код.
- Желательно, чтобы был понятный пользователь: кто пользуется и какую боль закрывает.
- Хорошо, если есть связка AI + код + интеграция + упаковка результата.
- Для публичного GitHub важна безопасность: без секретов, личных данных, приватных баз и клиентской информации.
- Лучше 3-5 сильных кейсов, чем длинный список всего подряд.

## Shortlist для обсуждения

| Проект | Что показывает | Сила для портфолио | Риск публикации | Предварительная роль |
| --- | --- | --- | --- | --- |
| Секретарь собраний | Telegram-бот, AssemblyAI, diarization, summary pipeline, Local Bot API для больших файлов | Очень сильный практический кейс | Проверить `.env`, записи, приватные стенограммы | Главный кейс |
| Нутрициолог | Фото еды, КБЖУ, дневник, LLM-чат, Supabase, VPS/systemd | Сильный продуктовый AI-бот | Проверить БД, пользовательские данные | Главный или дополнительный кейс |
| Second-brain | Голосовой бот, daily notes, Todoist, Obsidian, VPS-first vault | Сильный automation/productivity кейс | Высокая приватность личного vault | Скорее обезличенный case study |
| Poetry_Killer / PoetryForge | CLI-валидатор метра и рифмы, тесты, словари, LLM verification loop | Очень хороший developer-tool кейс | Низкий, если не публиковать лишние данные | Главный кейс |

## Скорее не брать в первую версию

| Проект | Причина |
| --- | --- |
| Office | Пока концепт / рабочее направление, мало готового артефакта |
| Учет доходов и расходов | Статус требует уточнения, локальный контекст шаблонный |
| HealthExport | Требует уточнения, вероятно содержит личные health data |
| FB-Downloader | Назначение требует уточнения |
| Evolution | Больше корпус/парсеры материалов, не очевидный портфельный AI automation кейс |
| Гайд по Сербии | Материалы и парсер, нужно понять продуктовую завершенность |
| ТГ-канал | Материалы, не самостоятельный automation-проект |
| Справочная информация | Справочная зона, не продукт |
| Архив проектов | Неактивные проекты |

## Возможная структура финального портфолио

### Вариант A: AI automation engineer

1. Секретарь собраний — speech-to-text для встреч.
2. Нутрициолог — продуктовый AI-бот с базой и ежедневным workflow.
3. Second-brain — персональная productivity automation.
4. PoetryForge — developer tool для проверки LLM-результатов.
5. Wiki_LLM — агентная инфраструктура и knowledge management.

### Вариант B: Prompt engineer + automation

1. Секретарь собраний — LLM summary и speaker mapping.
2. VoiceToText — транскрипция + ручной GPT-редактор.
3. PoetryForge — модель генерирует, инструмент проверяет, модель исправляет.
4. Wiki_LLM — правила, skills, wiki, агентные workflows.
5. Юрий или Second-brain — domain-specific assistant, только после проверки приватности.

### Вариант C: Осторожный публичный GitHub

1. PoetryForge — можно показывать кодом.
2. VoiceToText — можно показывать кодом после чистки.
3. Секретарь собраний — можно показывать кодом после чистки.
4. Wiki_LLM — частично, как документацию и workflow.
5. Second-brain / Олег / Почта — только обезличенные case studies без приватных данных.

## Следующие вопросы для выбора кейсов

- Что важнее показать комиссии: prompt engineering, automation, Python/backend, продуктовый подход или все вместе?
- Можно ли публично показывать код `Секретарь собраний`, `VoiceToText`, `PoetryForge`?
- Какие проекты уже имеют достаточно чистый README и запуск?
- Какие проекты содержат `.env`, базы, личные данные или клиентскую информацию?
- Нужны ли демо-скриншоты или достаточно README/case study?
